# Surface 1 — api.php sudo-bypass check

**Verdict:** ✅ **PASS — no findings**
**Date:** 2026-05-10
**Method:** Source inventory (Claude Explore agent) cross-referencing api.php dispatch table against every caller of `ipam_sudo_verify` / `ipam_sudo_require` / `ipam_sudo_consume_once` / `ipam_sudo_invalidate` in `Simple-PHP-IPAM/*.php`.

## Hypothesis

Sudo-class admin actions exposed via api.php with API key auth could bypass v3.27.0 step-up. If true, an API key (even an admin-grade one) could perform vault-key reveal, MFA disable, step-up policy mutation, or db-import without the step-up flow the web UI enforces.

## Finding

**Zero sudo-class operations are reachable via api.php.** The sudo-gated web actions inventoried below all have **no API equivalent** — not a "the API equivalent forgets to call sudo verify," but rather "no API handler exists for this operation at all."

## Sudo-class web actions × API exposure

| `backup_admin_destinations.php:451` vault_reveal/set/replace | `ipam_sudo_require` | — | n/a |
| `change_password.php:94` disable TOTP | `ipam_sudo_require` | — | n/a |

| `settings_reveal.php:61` reveal encrypted setting | `ipam_sudo_require` | — | n/a |
| `settings.php:122,297` step-up policy save | `ipam_sudo_require` (dynamic policy via `ipam_sudo_proposed_policy_from_overrides`) | — | n/a |

> Note: `users.php` set_role and delete intentionally do not call sudo_require per current design. They rely on admin role + the "cannot demote/delete last active admin" + "cannot self-action" guards. This is a separate design question (raised by Pass A architectural review), but not a Pass C bypass.

## Auth enforcement on the API dispatcher itself

- All write methods (`POST`/`PUT`/`DELETE`) are blocked for readonly API keys at `api.php:162`.
- All mutating handlers are reached only after `$apiKey` is populated from `Authorization: Bearer …` (lines 114–153). No unguarded write endpoint.
- `api_scan_run` (`api.php:2551`) re-checks the readonly flag belt-and-suspenders.
- Every mutating handler logs via `api_audit($db, $apiKey, …)` — audit trail includes the API key name.

## Design observation (not a finding)

The reason there is no sudo-bypass is structural: API keys are stateless (no session) and step-up auth is session-scoped (sudo grant lives in `$_SESSION`). The two models are fundamentally incompatible. Adding sudo-class actions to the API in the future would require either (a) an alternative re-proof mechanism (e.g. a one-time confirmation token in the request body) or (b) gating those operations to admin sessions only.

This means: **if someone ever proposes adding API endpoints for vault key reveal, MFA disable, db import, etc., that proposal triggers a design discussion**, not "just call `ipam_sudo_require` from the API handler" (which wouldn't work because there's no session to grant against). Capture this in the v3.28.0 / step 8 architecture review.
