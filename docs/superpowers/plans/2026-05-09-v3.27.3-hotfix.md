## Per-bug commit chain (TDD-first)

Each bug is one chain: failing test → fix → green test. Local gate green between chains.

### Bug 1 — #1127 (P0): Restore-staging session-state refactor

**Why P0**: install with `app_secret` blank (the documented v3.26.0+ post-vault-relocation state) cannot restore from any remote destination. Confirmed live by Sean on the mysql testing instance: `Stage failed: ipam_restore_wizard: cannot sign without app_secret`.

**Failing test (commit 1)**: `tests/RestoreStagingNoAppSecretTest.php` — bootstrap an in-memory environment with `app_secret = ''`, simulate the staged-file flow (stash + retrieve via the new helper), assert the round-trip works end-to-end without throwing. Pre-fix this fails because the existing `ipam_restore_sign()` throws `RuntimeException('cannot sign without app_secret')`.

**Fix (commit 2)**: 
- New helpers in `lib/backup.php`:
  - `ipam_restore_stage_pending(array $meta): void` — stashes `['path', 'meta', 'expires' => time() + 600]` in `$_SESSION['_pending_restore']`.
  - `ipam_restore_consume_pending(): ?array` — returns the staged-meta if expiry is fresh, else null. Single-use (`unset`).
- `download_remote_backup.php` calls `ipam_restore_stage_pending(...)` instead of `ipam_restore_sign(...)`. The form rendered to the user has NO path field — only action verbs.
- `backup_admin.php` apply-step calls `ipam_restore_consume_pending()` instead of `ipam_restore_verify_signed(...)`. Refuses on null.
- Old helpers `ipam_restore_sign` / `ipam_restore_verify_signed` deleted; call sites updated.

**Green test + cleanup (commit 3)**: rerun — passes. Also: add a regression test that submitting an empty session blocks apply (refuses with clear error). And: add a stored-XSS / form-replay regression — the apply step must NOT accept a `staged_path` field even if one is POSTed.

### Bug 2 — #1131 (P1): OIDC step-up replays original action

**Why P1**: same architectural pattern as #1127 (server-side state across redirects). Operator clicks Reveal → OIDC re-auth → lands back without seeing the key. Forces a second click. For some sudo-class actions (e.g., `disable_totp`) the second-click pattern works; for `vault_reveal` it's broken UX.

**Failing test (commit 1)**: `tests/SudoOidcActionReplayTest.php` — at step-up render time, simulate stashing a pending action via the new helper. After OIDC completion, assert the helper returns the pending action context, and a destination handler can re-execute the original POST equivalent. Pre-fix this fails because no such mechanism exists.

**Fix (commit 2)**:
- New helpers in `lib/auth_step_up.php`:
  - `ipam_sudo_oidc_stash_pending(array $context): void` — `$_SESSION['_sudo_oidc_pending']` with target URL, fields, csrf, expires.
  - `ipam_sudo_oidc_consume_pending(): ?array` — returns + unsets.
- All sudo-class handlers that render step-up inline (`vault_reveal/set/replace`, `disable_totp/email_otp_disable/passkey_delete`, `api_keys.php` create, `db_tools.php` import, `settings.php` policy save) gain a stash call when the form's OIDC link is rendered.
- `ipam_sudo_oidc_reauth_complete()` (lib/auth_step_up.php:637) returns either the existing return URL OR a "/sudo-replay.php" landing that auto-POSTs the pending fields back to the original target.
- New `sudo_replay.php` page — tiny auto-submit form with the pending fields + CSRF re-validation. Single-use.

**Green test (commit 3)**: rerun. Add wiring tests that all handlers in scope call the stash helper.

### Bug 3 — #1134 (P1): IP-level lockout audit + UI visibility

**Why P1**: defense-in-depth gap. Operator can't diagnose "why can't I log in from this IP" without server-side log diving. No audit trail for IP-level rate-limit firings.

**Failing test (commit 1)**: `tests/IpLockoutVisibilityTest.php` — simulate N failed login attempts from the same IP to trip `auth_rate_limited('login', $ip, ...)`. Assert (a) an `auth.ip_rate_limited` audit row exists, and (b) login attempts during the lockout window return a distinguishable error message (not the generic "wrong password"). Pre-fix both fail.

**Fix (commit 2)**:
- `login.php` (or wherever the rate-limit branch is) writes a new audit row `auth.ip_rate_limited` with the IP, attempts count, and unlock_at timestamp. First fire of a window only — not on every refused attempt within the window.
- The login response distinguishes IP-rate-limited from wrong-password: a "Too many failed attempts from this IP. Try again in N minutes." banner rendered on the login page.
- `docs/internal/audit-actions.md` updated with the new action verb.

**Green test (commit 3)**: rerun. Confirm no double-emission on subsequent attempts within the same window.

### Bug 4 — #1130 (LOW): api.php docblock fix

**Fix**: edit the docblock comment in `Simple-PHP-IPAM/api.php`. One-line.

### Bug 5 — #1129 (LOW): invalid settings tab UX

**Failing test**: `tests/SettingsInvalidTabRedirectTest.php` — `GET /settings.php?tab=garbage` should either (chosen direction) emit a soft banner `The requested tab no longer exists; showing General instead.` OR redirect to `?tab=general`. Pre-fix it silently falls back without any indication.

**Decision below — banner or redirect**: lock during commit 1.

**Fix**: edit the tab-resolver in `Simple-PHP-IPAM/settings.php`.

**Green test**: rerun.

### Bug 6 — #1128 (LOW): curl_close removal

**Failing test**: `tests/NoCurlCloseInCodebaseTest.php` source-level grep — assert no `curl_close(` calls anywhere under `Simple-PHP-IPAM/` (excluding tests + vendor). Pre-fix 7 hits.

**Fix**: delete all 7 `curl_close($ch)` calls (5 in `lib/S3Client.php`, 2 in `lib.php`'s webhook deliver).

**Green test**: rerun. PHP handles cleanup automatically.
