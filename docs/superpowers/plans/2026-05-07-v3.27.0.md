# v3.27.0 — Configurable step-up authentication for sensitive admin actions

**Status:** planning
**Author:** Sean Mousseau / Claude session 2026-05-07
**Origin:** v3.26.0 post-release bug report — OIDC-only admins cannot manage the backup vault key

---

## 1. Bug summary (the trigger)

Two defects landed in v3.26.0 (#1098, the vault-key admin panel):

1. **OIDC-only environments cannot set, replace, or reveal the backup vault key.** All three actions in `lib/backup_admin_destinations.php:430-445` re-prompt for the local admin password (`password_verify($supplied, $hash)`). OIDC-only users have a locked password hash (`password_hash` starts with `!`) and the handler refuses unconditionally. There is no escape hatch.
2. **The reveal control is not discoverable.** It is wrapped in a `<details><summary>Reveal current vault key</summary>` (view `views/backup_admin_destinations.php:64`). On an install with a key already configured, an operator who never expands the disclosure will never realise reveal is available.

Bug 1 is a release blocker for OIDC-only deployments. Bug 2 is a UX defect that promotes user-error data loss (operators rotating the key without realising they could have copied the existing one first).

## 2. Why this is not v3.26.1

The naive fix — accept TOTP/passkey when the user has no password — patches the bug but doubles down on the problem: hardcoded policy in handler code. The project is on a v4.x trajectory toward enterprise auth (LDAP, SAML — see `docs/internal/v4-release-stream.md`). Each new provider would re-litigate "how do we step up an LDAP user?" from scratch. We need the gate to be **decoupled from the login provider** before we ship more providers.

So v3.27.0 reframes the bug as a missing primitive: **install-wide step-up auth policy**, with a single helper (`ipam_sudo_verify`) that all sensitive actions call. The two original bugs are fixed as a side effect of migrating the vault handler to the helper.

## 3. Design

### 3.1 The helper

```php
ipam_sudo_verify(\PDO $db, int $userId, array $proof): bool
```

Resolution order, evaluated against the install's `auth.step_up.*` policy:

1. **Cached grant.** If `$_SESSION['sudo_until_ts']` is in the future, return true without re-prompting. Refresh the TTL on use.
2. **Strong MFA proof.** If the policy permits and the user has an enrolled method matching the supplied proof:
   - TOTP code → `ipam_totp_verify($secret, $code)`
   - Email OTP → existing `email_otp_*` verify path
   - WebAuthn assertion → `lbuchs/webauthn` verify path
3. **Provider re-auth fallback.** If the policy permits "provider re-auth":
   - Local user (has usable password hash) → `password_verify($proof['password'], $hash)`
   - OIDC user → return false from this call; caller redirects to OIDC `/oidc/start.php?prompt=login&return_to=...` and verifies via the IdP's authentication response. Future LDAP/SAML providers add their own branches.
4. **Refusal.** If no permitted method satisfies the gate, return false. The caller surfaces an actionable error (e.g. "Enroll TOTP or contact your administrator to allow provider re-auth").

On success, write `$_SESSION['sudo_until_ts'] = time() + $ttl` and `$_SESSION['sudo_method']` (audit detail). Audit row: `auth.sudo_passed` with method + IP. On failure: `auth.sudo_failed` with attempted method + IP. Rate-limit failures via existing `record_auth_failure` / `auth_rate_limited` against the bucket `sudo`.

### 3.2 Policy schema (registry entries via `ipam_setting_definitions()`)

| Key | Type | Default | Notes |
|---|---|---|---|
| `auth.step_up.allow_totp` | bool | true | Disabled in UI if no admins have TOTP enrolled. |
| `auth.step_up.allow_email_otp` | bool | true | Disabled in UI if SMTP is not configured. |
| `auth.step_up.allow_webauthn` | bool | true | Disabled in UI if no admins have a passkey. |
| `auth.step_up.allow_provider_reauth` | bool | true | Local password verify or OIDC `prompt=login`. |
| `auth.step_up.ttl_seconds` | int | 300 | Discrete options 0/60/300/900/1800/3600. Validated server-side. |

Default seed values are **permissive** to match existing v3.26.0 behaviour as closely as possible: any enrolled MFA method satisfies, plus password fallback for local users. This means the v3.26.0 → v3.27.0 upgrade is behavior-preserving for password-MFA admins and bug-fixing for OIDC-only admins.

### 3.3 Lock-out precondition

Before persisting a policy save, validate that **at least one active admin can satisfy the proposed policy**. Same shape as the existing last-active-admin guard in `users.php`. Expressed as: for every active admin, can they pass at least one permitted method? If no admin can pass *any* permitted method, refuse the save with a specific error naming the missing capability.

### 3.4 Self-protection

Saving the step-up policy is itself a sudo action gated by `ipam_sudo_verify()` under the **current** policy. Audit row: `auth.step_up_policy.updated`. Tightening the policy invalidates all in-flight sudo grants (`$_SESSION['sudo_until_ts'] = 0`) so the new rule applies on the next sensitive action.

### 3.5 Sudo grant invalidation

`$_SESSION['sudo_until_ts']` is unconditionally cleared on any of:

- logout
- session regeneration after password change
- role downgrade (admin → readonly)
- `oidc_sub` change on the user row
- MFA enrollment change (TOTP enroll/disable, passkey add/delete, email OTP enroll/disable)
- step-up policy update

### 3.6 Audit vocabulary

New action strings (added to `docs/internal/audit-actions.md`):

- `auth.sudo_passed` — successful step-up; details=`method=<m> ip=<ip>`
- `auth.sudo_failed` — failed step-up; details=`method=<m> ip=<ip> reason=<r>`
- `auth.sudo_rate_limited` — sudo rate limit hit; details=`ip=<ip>`
- `auth.step_up_policy.updated` — policy save; details=`methods=<csv> ttl=<sec> by=<u>`

Existing `backup.vault_key.sudo_failed` action is retained as an alias of `auth.sudo_failed` for one release to avoid log-query breakage; deprecated in v3.28.0.

## 5. UI changes

### 5.1 New admin card: "Step-up authentication"

New card on a security-settings page (location TBD during implementation — likely a new `security_settings.php` admin page, or a section of an existing admin page). Two controls:

- **Acceptable methods** — checkbox group of {TOTP, Email OTP, WebAuthn passkey, provider re-auth fallback}. Each checkbox shows greyed-out + helper text when the underlying capability is unavailable on the install (e.g. "SMTP not configured" disables Email OTP).
- **Re-prompt timeout** — discrete dropdown: `Every action / 1 min / 5 min (default) / 15 min / 30 min / 1 hour`. No free-text input.

Saving requires step-up under the current policy. Lock-out precondition validated before save.

### 5.2 Reveal vault key — promote out of `<details>`

Replace the collapsed disclosure at `views/backup_admin_destinations.php:62-78` with a primary `[Reveal vault key]` button placed next to the fingerprint. Set/Replace remain a button group beneath. Sudo prompt opens inline on click (or via a small drawer — to be decided during build).

### 5.3 Step-up prompt UX

When a sensitive action triggers `ipam_sudo_verify()` and no cached grant exists, the page renders an inline form titled "Confirm your identity to continue" with:

- Method chooser (defaults to user's strongest enrolled method, narrowed by current policy)
- Method-specific input field (TOTP code, Email OTP code, passkey browser prompt, password)
- Submit button → POSTs back to the same handler with the proof; on success the original action proceeds.

Implementation note: prefer a single shared partial (`views/_step_up_prompt.php`) so all eight call sites render identically.

## 6. Migration

Single migration in `migrations.php` keyed `2026.05.27-001-step-up-policy` (natural-sort order; lands between v3.26.0 and v3.27.0 entries):

1. Insert default policy rows into the settings table for the five `auth.step_up.*` keys (4 bools + 1 int).
2. No schema changes — settings table already exists.

Idempotent: uses `INSERT OR IGNORE` (SQLite) / `ON CONFLICT DO NOTHING` (Postgres) / `INSERT IGNORE` (MySQL) via `Dialect::upsert_or_ignore`.

## 8. Out-of-scope (deferred)

- Generic step-up framework for non-admin actions (no current need).
- Per-action policy overrides (e.g. "vault_reveal needs passkey, everything else accepts TOTP"). Could be added later as `auth.step_up.action_overrides` if a real use case appears; speculative now.
- LDAP / SAML provider re-auth wiring — those providers don't exist yet; the helper has the branch but the implementation lands with the provider.
- Sudo-mode UI affordance ("you have N seconds of sudo remaining" indicator). Nice-to-have.
- Enforcement of strong MFA enrollment (forcing admins to enroll). Separate roadmap item.

## 9. Lessons-learned (to promote after release)

After v3.27.0 ships, add to `docs/internal/lessons-learned.md`:

- **Hardcoded auth policy is a v4 footgun.** When new auth providers are on the roadmap, gates that spell out one provider's primitive (e.g. `password_verify`) become bugs the moment the second provider lands. Express sensitive-action gates as policy-resolved abstractions from day one.
- **Configurable defaults must be permissive at upgrade time.** A new policy row whose default is stricter than today's behaviour will lock out existing operators on upgrade. Default to "match current behaviour", let admins tighten.
- **Lock-out preconditions are a class of guard.** Last-active-admin guard, last-passkey guard, and now last-can-satisfy-policy guard are the same shape: "do not allow the operator to leave the system in a state with no path back in."
