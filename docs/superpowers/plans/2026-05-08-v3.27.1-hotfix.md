# v3.27.1 — Backup encrypt-side vault wiring + observability hardening

**Status:** analysis (not yet a plan — awaiting design sign-off before any code)
**Author:** Sean Mousseau / Claude session 2026-05-08
**Origin:** Production scheduled backups silently failing on `ipam.seanmousseau.com` since 2026-05-07. Investigation traced the failure to a previously-undiscovered architectural gap that spans v3.24 → v3.26 → v3.27.

> **Read this before any other section:** the bug isn't a one-line oversight. It's a "primitive added, reads migrated, writes never migrated" gap that hid behind the legacy `app_secret` path for two minor releases. The hotfix is small, but understanding why we shipped a half-finished feature three times is the part that protects us next time.

---

## 1. The original report

> "Production system. Backups don't seem to be working and I am worried there's a bug." — sean, 2026-05-08 ~20:09 EDT

Triage on prod (`ipam.seanmousseau.com`, MySQL, OpenLiteSpeed, deployed v3.27.0 earlier the same day) revealed:

- Last successful scheduled backup landed in Wasabi at **2026-05-06 16:30 EDT** (`backup_runs.id=19`, source_version 3.23.0).
- Two consecutive scheduled runs (May 7 night, May 8 night) advanced `backup_schedules.last_run_at` but produced **no `backup_runs` row, no `backup.run` audit, no `backup.failed` audit, no log line**.
- Forced cron run with stderr captured surfaced `[backup_schedule] ERROR: schedule_id=2 ipam_backup: encryption requested but app_secret is empty`.
- Subsequent test with `default_encryption_mode='unencrypted'` produced the **same** error because the orchestrator coerces `unencrypted → stored` for non-`local` destinations (`lib/backup.php:367-374`).
- Operator (sean) had separately attempted to set the vault key on May 7 night via the admin UI and hit `backup.vault_key.sudo_failed`; succeeded on May 8 night (`backup.vault_key.set` audit row 2602). Vault key was successfully persisted (DB envelope present, `bootstrap_key` injected into `config.php`).

The vault key existing in the DB *should* have been enough for the scheduled backup to succeed. It wasn't.

## 2. Glossary — five keys, three formats, easy to confuse

| Name | Where it lives | Length | First shipped | What it protects |
|---|---|---|---|---|
| `app_secret` | `config.php` | 32 bytes (any) | pre-v3.x | Legacy IPAMBKP1/IPAMBKP2 backups, TOTP secret encryption-at-rest, internal HMAC sigs. **Optional** in v3.26.0+ if you only use IPAMBKP3 backups and don't enroll TOTP-encrypted-secrets — but no install has been told to remove it. |
| `bootstrap_key` | `config.php` | 32 bytes | v3.26.0 (#1098 part A) | Wraps/unwraps `backup_vault_key` envelopes via libsodium `crypto_secretbox`. Auto-generated on first vault-key write. Never sent to the DB. |
| `backup_vault_key` | `settings` row, wrapped under bootstrap_key | 32 bytes | v3.26.0 (#1098 part A) | The actual key that protects IPAMBKP3 stored-mode archives. Never persisted in raw form. |
| (operator passphrase) | not stored | any | v3.24.0 (#836) | IPAMBKP3 transitory mode, derived to a key via Argon2id at encrypt and decrypt time. |
| (no key) | n/a | n/a | always | Plain `.sql.gz` (legacy) or `.ipambkl1.gz` (v3.23.0+) for unencrypted backups (Local destinations only). |

| Format | Magic | Encrypted with | First shipped | Status |
|---|---|---|---|---|
| IPAMBKP1 | `IPAMBKP1` | `app_secret` (AES-GCM, random IV) | early v3.x | Legacy. Restore still supported. |
| IPAMBKP2 | `IPAMBKP2` | `app_secret` (streaming AES-GCM) | v3.7-ish | Legacy. **Currently the format every scheduled encrypted backup is being written as.** |
| IPAMBKP3 | `IPAMBKP3` | `backup_vault_key` (stored) or operator passphrase (transitory) | v3.24.0 (#836) | Modern. **Ships with a working encrypt + decrypt codec but no caller produces it on the scheduled-backup path.** |
| IPAMBKU1 | `IPAMBKU1` | n/a (integrity-only HMAC under `app_secret`) | v3.24.0 (#837) | For operator-uploaded restore staging. Not relevant here. |
| IPAMBKL1 | `IPAMBKL1` | n/a (logical dump body, gzip) | v3.23.0 (#824) | Engine-agnostic logical backup. Orthogonal to encryption — an IPAMBKL1 dump can be wrapped in any of IPAMBKP1/2/3. |

The combinatorial space is `format × encryption × triggered_by × destination_type`, which is why the bug took until production to fall out — many cells were never exercised end-to-end on a fresh install with an empty `app_secret`.

The crucial confusion: the v3.26.0 plan section "F-VAULT-RELOC: vault-key relocation + legacy runner retirement" sounded comprehensive. It wasn't. It accomplished:

- ✅ helpers (`ipam_vault_wrap`, `ipam_vault_unwrap`, `ipam_bootstrap_key`)
- ✅ migration (DB row + settings registry entry)
- ✅ admin UI (set/replace/reveal)
- ✅ restore-side reads `ipam_backup_vault_key_get_raw()` first
- ❌ **orchestrator (`lib/backup.php:316–505`) was never updated** — still calls `ipam_backup_encrypt_to_tmp($tmpSql, $appSecret)` which calls `backup_encrypt_stream` which produces IPAMBKP2

The legacy backup runner retirement (#1059) muddied the picture further: by removing the legacy single-destination runner, v3.26.0 made the unified schedule loop the only encrypt-side caller. The unified loop was the one that hadn't been migrated. Net effect: every scheduled encrypted backup on every install since v3.24.0 has been IPAMBKP2 — with the failure mode invisible until `app_secret` is empty.

## 4. The actual bug (precisely)

### 4.1 Orchestrator path

`lib/backup.php:316–505` — `ipam_backup_run_for_destination()`:

```
ipam_backup_reap_stale_runs()                      [line 327]
ipam_backup_active_run_id()                        [line 328]   — concurrency guard
ipam_backup_dest_load()                            [line 339]
ipam_backup_dest_client()                          [line 347]
resolve $backupType, $encMode                      [lines 354–374]
  ↳ Server-side guard: encMode='unencrypted' on
    non-local destination → coerced to 'stored'
    (lines 372–374)
ipam_backup_logical_dump() OR ipam_backup_dump_to_tmp()
                                                   [lines 378–394]
$appSecret = $config['app_secret'] ?? ''           [line 396]
if ($encMode !== 'unencrypted'):
  if ($appSecret === ''): THROW ←← BUG SITE        [lines 397–401]
  $tmpFile = ipam_backup_encrypt_to_tmp(           [line 402]
      $tmpSql, $appSecret)
                                                   ↳ produces IPAMBKP2
ipam_backup_insert_log()                           [line 413]   — backup_runs row created HERE
upload                                             [line 442]
audit('backup.run' / 'backup.failed')              [lines 458, 488]
ipam_backup_finalize_schedule_run()                [cron.php:447]
  ↳ runs in finally-like path; advances last_run_at
    AND next_run_at regardless of success/failure
```

The entire span between line 327 and line 413 has **zero forensic output** if it throws. No `backup_runs` row, no `backup.failed` audit, only stderr from the cron wrapper's `$fail()` callback — which on prod is `> /dev/null 2>&1`.

### 4.2 What restore does instead (the template we should mirror)

`lib/backup.php:1241–1266`:

```php
$appSecret = is_string($config['app_secret'] ?? null) ? $config['app_secret'] : '';
$vaultKey = ipam_backup_vault_key_get_raw();
if ($appSecret === '' && $vaultKey === null) {
    throw new RuntimeException(
        'ipam_restore: encrypted backup but neither app_secret nor backup_vault_key is set'
    );
}
backup_decrypt_to_path($downloadPath, $stagedPath, $appSecret, null, $vaultKey);
```

The dispatcher (`backup_decrypt_to_path` → eventually `backup_decrypt_stream_dispatch`) peeks the magic bytes and routes to IPAMBKP1/2 (using `$appSecret`) or IPAMBKP3 (using `$vaultKey`). **Read side is correct.** Write side just needs the same shape.

### 4.3 Five silent-failure gaps that compound the bug

Even with the encrypt path fixed, today's observability would hide a future variant of this bug equally well. Each gap independently is a defect; together they make a quiet failure indistinguishable from a healthy install.

| # | Gap | Site |
|---|---|---|
| O1 | `cron.php $fail()` only writes `STDERR` — no `audit()`, no `error_log()` (the latter would survive `> /dev/null 2>&1` because it goes to the SAPI error log file). | `cron.php:118-122` |
| O2 | Production cron entry redirects `2>&1` to `/dev/null`. The wrapper script `/root/scripts/ipam-cron.sh` does the same. **The recommended `>> /var/log/ipam-cron.log 2>&1` from the inline doc at `cron.php:19` was never wired into deploy-targets.md or `upgrade.sh`.** | ops |
| O3 | `backup_runs` row is INSERTed at `lib/backup.php:413` — **after** dump and encrypt. Anything throwing in lines 327–412 produces no row in History UI, no row to filter on, no row to attach `error_message` to. | `lib/backup.php:316–413` |
| O4 | Audit on backup failure only fires inside the upload-phase try/catch at `lib/backup.php:458`. Pre-upload throws have no audit. The existing audit-action vocabulary has no `backup.preflight_failed` row to write. | `lib/backup.php:316–442` + `docs/internal/audit-actions.md` |
| O5 | `ipam_backup_finalize_schedule_run()` always advances `last_run_at` and `next_run_at`, regardless of outcome. The schedule-overdue detector (`ipam_backup_detect_overdue_schedules`, cron Task 6d) reads only `next_run_at` to determine overdue-ness. **A schedule firing a hundred times that all throw before INSERT is indistinguishable from a healthy schedule that hasn't yet hit its next slot.** Operators rely on the email alert to catch breakage. The alert can't see this. | `lib/backup.php` overdue detector |

These five are why this bug has been live since v3.24.0 (when IPAMBKP3 was introduced and the IPAMBKP2 code was no longer the design intent for new installs) but only surfaced now: any install with `app_secret` set kept silently producing IPAMBKP2 archives. Restore worked. Nobody noticed. The first install where `app_secret` is empty *and* the operator went through the v3.26.0 vault setup is the first install that visibly breaks.

## 5. Why the failure was specifically silent on prod

Reading the data we have (audit log, `backup_runs`, `backup_schedules`, file mtimes), reconstructed in chronological order:

The investigation confirmed the silent-failure pattern by *forcing* the schedule (`next_run_at = utc_timestamp() - 1 minute`) and running cron manually with stderr captured. The same throw fired immediately. With the destination flipped back to `default_encryption_mode='unencrypted'`, it threw the same message — because the server-side `unencrypted → stored` coercion at `lib/backup.php:372-374` makes "unencrypted on a remote destination" structurally impossible. The check was added in #851 (v3.25.0) for sound reasons (you don't want plaintext SQL dumps sitting in S3) but it forecloses the only escape hatch from the encrypt-side bug.

## 6. Proposed fix design

### 6.1 Encrypt-write path — three branches

Replace `lib/backup.php:396-408` with the same shape as the restore-side dispatcher:

```php
$appSecret = is_string($config['app_secret'] ?? null) ? $config['app_secret'] : '';
$vaultKey  = ipam_backup_vault_key_get_raw();   // null if not configured

if ($encMode !== 'unencrypted') {
    // Prefer vault key when present — produces IPAMBKP3 stored. Fall back
    // to app_secret for legacy installs (produces IPAMBKP2). Refuse if
    // neither is available, so the operator can act.
    if ($vaultKey !== null) {
        $tmpFile   = ipam_backup_encrypt_v3_stored_to_tmp($tmpSql, $vaultKey);
        $extension = '.ipambkp3';
    } elseif ($appSecret !== '') {
        $tmpFile   = ipam_backup_encrypt_to_tmp($tmpSql, $appSecret);
        $extension = '.enc';
    } else {
        @unlink($tmpSql);
        throw new RuntimeException(
            'ipam_backup: encryption requested but neither backup_vault_key '
            . 'nor app_secret is configured. Set up the backup vault key in '
            . 'Backups → Destinations, or restore app_secret in config.php.'
        );
    }
} else {
    $tmpFile   = $tmpSql;
    $extension = $dumpExt;
}
```

Notes:

- `ipam_backup_encrypt_v3_stored_to_tmp($srcPath, $rawVaultKey): string` — new helper, mirrors `ipam_backup_encrypt_to_tmp()`'s `tempnam`/wrap/error pattern. Internally calls the existing IPAMBKP3 encrypt codec at `lib.php:5061+` in stored mode.
- Filename suffix `.ipambkp3` (proposal — open question, see §9 Q1) clearly distinguishes vault-key-protected from app_secret-protected archives in remote storage and in History.
- The IPAMBKP3 transitory mode (operator passphrase) is intentionally **not** exposed on the orchestrator path — there's no operator at scheduled-backup time. If an operator wants per-archive passphrase protection they use the manual run-now flow with a separate prompt (out of scope for this hotfix; track separately).

### 6.3 What we are NOT changing in this hotfix

- **No migration.** The schema is fine. Only behavior changes.
- **No new runtime dependencies.** All helpers exist already; we wire the orchestrator to existing IPAMBKP3 encrypt code.
- **No deprecation of `app_secret` encryption.** Installs with `app_secret` set and no vault key keep working unchanged. We surface the modern path; we don't yank the legacy path.
- **No legacy-archive re-encryption tool.** Existing IPAMBKP2 archives in remote storage stay valid; the restore dispatcher already handles them. A re-encrypt tool is post-v3.28.0 backlog.

### 6.4 Bug X — `sudo_once` never consumed (in v3.27.1)

Per §9.1: `ipam_sudo_consume_once()` is defined but never called.

**Fix shape:**

1. Audit the 10 sudo-class handler call sites enumerated in the architecture audit (`api_keys.php`, `change_password.php` ×3, `db_tools.php`, `lib/backup_admin_destinations.php`, `settings.php` ×2, `settings_reveal.php`, `step_up.php`).
2. Each handler calls `ipam_sudo_consume_once()` immediately after the gated action's side effect commits (audit row written, redirect headers prepared, but before the redirect itself for handlers that redirect — so a re-execution of the request would correctly require re-auth).
3. **Decision:** consume on success only, OR consume always (success + failure)?
   - **Consume on success only:** matches the docstring ("after the action runs **successfully**"). Risk: a partial-failure path that surfaces an error message keeps the grant warm; a follow-on user click on a different sudo action would short-circuit. Security-weaker.
   - **Consume always:** more conservative. Failed action → user reproves to retry. Matches "re-prompt every action" more literally. Slight UX cost on benign failures (e.g., "name required" inline validation triggering a re-auth on retry). Security-stronger.
   - **Recommendation:** consume always. UX cost is bounded (operator already knows they're on TTL=0 = strictest mode). Update `ipam_sudo_consume_once()` docstring at `lib/auth_step_up.php:86-90` to match.
4. Tests (PHPUnit `tests/SudoVerifyTest.php`):
   - `testTtlZero_GrantConsumedAfterAction()` — set policy ttl=0, prove, observe `sudo_once=true`, simulate consume, assert `sudo_once` cleared.
   - `testTtlZero_TwoSudoActions_RequireTwoProofs()` — under ttl=0, action #1 mints + consumes; action #2 must re-prove (regression test for the bug we're fixing).
   - `testTtlZero_PolicySetButZeroHandlersConsume_ProducesSessionLongGrant()` — explicit assertion of the bug behaviour against an unfixed handler (lock the regression in place).
5. Audit the rest of the codebase quarterly for "function defined but never called" — track the cleanup item in `docs/internal/cleanup.md` so this pattern surfaces earlier next time.

## 7. Risks and edge cases

| Risk | Likelihood | Mitigation |
|---|---|---|
| Operator with `app_secret` set AND vault key set — does the orchestrator pick the right one? | High (every install that goes through the v3.26.0 → vault setup migration without removing `app_secret`) | Decision: vault key wins. Document in CHANGELOG and `docs/internal/auth-model.md`. Add a one-line "Active backup encryption: IPAMBKP3 (vault key)" indicator to the destinations admin so the operator can see what they're getting. |
| Operator with neither set, but `default_encryption_mode='stored'` — orchestrator throws, schedules fail. | Medium (rare in practice; current prod is exactly this state until tonight's vault setup) | The thrown error message explicitly tells the operator how to fix it. The new pre-INSERT failed `backup_runs` row + `backup.preflight_failed` audit row makes the failure unmissable in the UI. |
| Operator with ONLY `app_secret` (no vault key) — should they see a UI nudge to migrate? | Low blast radius if we don't | Not in this hotfix. Open a v3.28.0 issue: "soft-warn destinations admin when on legacy IPAMBKP2 path." |
| Existing in-flight test fixtures hardcode IPAMBKP2 expectations | Medium | PHPUnit + Playwright spec audit. The existing `step-up-vault-flow` Playwright spec already exercises a vault-key generate; verify it round-trips a backup post-fix. |
| Restore of an IPAMBKP3-protected archive on an install where vault key was lost | Low (operator error) | Already handled — `backup_decrypt_to_path` throws an actionable message; nothing changes in this hotfix. |
| Race: two cron ticks both hit "no vault key, no app_secret" at the same time and both write a `backup.preflight_failed` audit | Low | Fine. The audit log accepting duplicates is correct; we want every failed attempt recorded. |
| Production rollback path (we ship v3.27.1, find a regression, need to revert) | Medium | Hotfix preserves all schema + storage + audit behavior. Rollback to v3.27.0 returns to silent-failure state — bad but recoverable. SHA256SUMS frozen. Per `docs/internal/deploy-targets.md` rollback procedure. |

### 9.4 Bug Z — REPRODUCED via OIDC step-up (Pass A live, 2026-05-08 22:06 EDT)

**Sean's original report — now fully understood and reproducible.** The bug only manifests on the OIDC re-auth method because that's the only step-up path that goes through `ipam_sudo_oidc_reauth_redirect_url()` and its broken return-path validator at `lib/auth_step_up.php:480-489`.

**Code-level root cause:**

```php
// lib/auth_step_up.php:480-489
$safe = 'destinations.php';
if ($returnPath !== ''
    && $returnPath[0] === '/'              // ← REQUIRES absolute path
    && !str_starts_with($returnPath, '//')
    ...) {
    $safe = $returnPath;
}
```

The validation rejects every relative path. Vault key handler at `lib/backup_admin_destinations.php:467` passes `$redirectBase = 'backup_admin.php?tab=destinations'` — relative, no leading slash. Validator falls back to hardcoded `'destinations.php'` (legacy page). After OIDC round-trip, user lands on the wrong page and the original action's POST is lost. Step-up succeeds but the action vanishes — silently. The user clicks the original button again on whatever page they end up on; warm sudo grant from the OIDC re-auth carries the second click through; only one `backup.vault_key.set` audit row results.

**Mirror validator at `step_up.php:30-49` accepts relative paths**, so the inconsistency between the two validators is itself the larger architectural finding: parallel sanitization functions for the same input class with different acceptance rules.

**Fix shape (one-liner):** rewrite `lib/auth_step_up.php:480-489` to accept relative paths (same logic as `step_up.php:30-49`'s `ipam_step_up_validate_return_to`), or rationalize to a single shared helper. Either approach. Pair with a PHPUnit test that asserts `'backup_admin.php?tab=destinations'` survives validation.

**Slot — RECOMMEND ESCALATING TO v3.27.1.** Original decision was v3.27.2 (per sean's "If reproduced, it must be delivered in .2"). New evidence after Pass A api_keys.php confirmation tip the call:

1. **Scope:** affects ALL 8 sudo-class call sites that pass relative `$stepUpReturnPath` (api_keys, change_password×3, db_tools, settings×2, vault). Static analysis + empirical confirmation on two of them. See §9.6 below.
2. **OIDC-only admin impact:** the v3.27.0 step-up subsystem's stated raison d'être (#1098 — fix the OIDC-only admin lockout) is structurally non-functional on v3.27.0 because of this bug. An OIDC-only admin can NEVER complete a sudo action; every attempt silently drops. They're effectively MORE locked out than under v3.26.0's hardcoded password prompt (which at least failed visibly).
3. **Fix size:** one-liner. Mirror `step_up.php:30-49`'s `ipam_step_up_validate_return_to` logic to also accept relative paths in `lib/auth_step_up.php:480-489`. Or rationalise to a single shared helper.
4. **PR locality:** v3.27.1 is already touching adjacent step-up code (Bug X consume_once wiring across the same 10 handlers). Folding Bug Z in is a same-area, same-PR change.

Sean's call but the scope argument is unambiguous. Treat as v3.27.1 unless there's a release-shape reason to defer.

### 9.5 Bug U — OIDC auto-provision creates users with real password hashes (Pass A live, 2026-05-08 22:06 EDT)

OIDC-provisioned users get a random bcrypt password hash instead of the `!disabled` sentinel that the OIDC-only-admin lockout protection model expects. Discovered during Pass A when the step-up prompt offered "Account password" as a method for `claude-oidc` — a user who has never had a known password.

**Effect:**
1. Step-up prompt offers a method the operator can never satisfy (UX confusion)
2. The OIDC-only-admin lockout precondition guard `ipam_sudo_policy_lockout_check()` evaluates `claude-oidc` as having a usable password method, so policy changes that should be refused (because they'd strand OIDC-only admins) are allowed through
3. The regression test `SudoVerifyTest::testLockedPasswordHashIsNeverAcceptedAsProof` (per `step-up-auth.md`) verifies the `!disabled` sentinel is rejected — but never fires in production because no auto-provisioned user has that sentinel

**Same pattern as the other bugs found today:** the v3.27.0 OIDC-only-admin support landed at the step-up gate but was never propagated to the auto-provision code path.

**Fix shape (one-liner):** in the OIDC auto-provision insert, set `password_hash = '!disabled'` instead of generating a random hash. Pair with regression test `assertEvery row with non-empty oidc_sub has password_hash starting with '!' or empty`.

**Slot:** v3.27.2. Same milestone as Bug Y for the same reason — both are step-up-era OIDC/lockout consistency bugs.

### 9.3 Bug V (uncovered during Pass A live, 2026-05-08 21:52 EDT) — settings.php boolean toggle wipes adjacent unsaved string fields

The OIDC settings group form contains text fields (`client_id`, `client_secret`, `discovery_url`, `redirect_uri`) AND boolean checkboxes (`auto_link`, `auto_provision`, etc.). The visible checkboxes are JS-bound to **separate per-key forms**: clicking a checkbox submits ONLY that single field via the per-key save path (`settings.php:97-170`). Page reloads with the GROUP form re-rendered from DB, and any text values the operator typed but didn't yet save in the group form are visually gone.

**Repro confirmed live in Pass A:** typed `BUG-REPRO-CLIENT-ID-12345` into client_id, clicked auto_provision checkbox, page reloaded with the DB value (sean's previously-saved `EDT7yd...`) and my test value vanished.

**Fix shape:** rationalise to a single form. Either (1) drop the per-key toggle path entirely and have all settings save through the group save handler, or (2) keep per-key but have its handler also consume any group-form fields present in the same POST. Option (1) is simpler and removes the divergence.

**Slot:** v3.27.2 with the rest of the "step-up era settings semantics" cluster.

### 9.2 Bug W (uncovered during Pass A regression — 2026-05-08 21:25 EDT)

**`ipam_vault_key_status()` precondition gate conflates IPAMBKP2 with IPAMBKP3.** The gate at `lib/backup_admin_destinations.php:515-528` reads `has_encrypted_runs` from `ipam_vault_key_status()` (`lib/backup_admin_destinations.php:347-360`), which queries:

```sql
SELECT 1 FROM backup_runs WHERE encryption_mode != 'unencrypted' LIMIT 1
```

That returns true for *any* encrypted run, IPAMBKP2 *or* IPAMBKP3. But IPAMBKP2 archives are encrypted with `app_secret` and are **completely independent of the backup_vault_key**. Setting up a vault key for the first time on an install with historical IPAMBKP2 archives does not orphan anything. Yet the gate refuses `vault_set + generate` and forces the operator into the `vault_set + paste` ("recover from password manager") path — which is nonsensical when the operator has never had a vault key before.

**Effect:** any install that:
- Was on v3.x with a destination configured `encrypt=1`
- Produced any scheduled backups before vault_key was even introduced (v3.26.0)
- Now wants to set up the vault key for the first time

… is blocked from the Generate path and forced to either delete encrypted backup history or paste a key they've never had.

**Fix shape (small):** the gate should distinguish IPAMBKP2 from IPAMBKP3 archives. Two options:
1. **Quick fix:** add a boolean column `backup_runs.is_vault_key_protected` defaulting `false`. Set on rows produced by IPAMBKP3 path. The gate reads that instead of `encryption_mode != 'unencrypted'`. Migration backfills false for all existing rows.
2. **Cleaner fix:** widen `encryption_mode` vocabulary to include `'stored_v2'` (app_secret) and `'stored_v3'` (vault_key) and update the gate accordingly. Migration uses filename suffix or magic-byte sniffing to backfill.

**Slot:** v3.27.1 (small, related to the same migration story we're already telling for the encrypt-write-path fix). Specifically: when the encrypt-write-path fix lands (which produces IPAMBKP3 with `.ipambkp3` suffix), all newly-produced encrypted rows can be tagged correctly. Backfilling existing IPAMBKP2 rows is a one-liner since they all have `.enc` suffix and IPAMBKP2 is the only thing that ever produced `.enc`.

**Test:** add to `tests/BackupEncryptDispatchTest.php` (planned for v3.27.1):
- `testFreshInstallVaultSetGenerate_NotBlockedByLegacyIPAMBKP2Archives()` — fixture has IPAMBKP2 archives + no vault key; assert `ipam_vault_key_status()['has_encrypted_runs']` is `false` (because none of the encrypted rows are IPAMBKP3); assert vault_set Generate succeeds.

### 9.1 Bugs uncovered during the Q&A walkthrough

While stepping through Q6, two additional v3.27.0 step-up subsystem bugs were discovered. Both are the same architectural pattern as the encrypt-write-path bug — documented behaviour the code doesn't deliver.

**Bug X — `sudo_once` never consumed (security regression).** `ipam_sudo_consume_once()` is defined at `lib/auth_step_up.php:91-94` and documented as the consumption mechanism for `ttl_seconds=0` ("re-prompt every action") policy. **Zero handlers call it across the entire codebase** (verified by repo-wide grep). Effect: TTL=0 grants persist as session-long warm grants, contradicting the policy registry's UI text. Operators tightening TTL to 0 thinking they're hardening their install are materially worse off than at any other TTL setting (which all expire).

**Bug Y — MFA-disable lockout vector.** `ipam_sudo_policy_lockout_check()` correctly guards the policy-save handler against stranding admins. The equivalent precondition check is **not present** in `change_password.php`'s `disable_totp` / `email_otp_disable` / `passkey_delete` handlers. A user with only TOTP enrolled can disable TOTP via step-up→TOTP, end up with zero step-up methods available, and be permanently stranded from every sudo action including re-enrolling TOTP.

**Slotting (locked):**
- **Bug X → v3.27.1** (security regression, small mechanical fix).
- **Bug Y → v3.27.2** (needs design: which actions get the guard, "is this your last method" UX message, interaction with self-protection guards).

## 10. Lessons learned (to promote after release)

These belong in `docs/internal/lessons-learned.md` after the hotfix lands. Pre-writing them here so they don't slip through.

1. **"Add a primitive, migrate the reads" is not the same as migrating the writes.** v3.26.0 shipped vault wrap/unwrap, the migration, the admin UI, and the restore-side dispatcher. The orchestrator's encrypt call site was overlooked because no test exercised the full encrypt → upload → restore round-trip with an empty `app_secret`. Future feature splits across "infrastructure / read / write" tracks need an explicit "is the write path wired?" gate.
2. **Silent failure has compounding gaps.** Five separate observability defects each reasonable in isolation produced a complete forensic blackout in combination. Treat observability as a property of the system, not as per-feature instrumentation.
3. **Coercion guards can foreclose escape hatches.** The `unencrypted → stored` upgrade for non-Local destinations (good) made it impossible to test the "no encryption" path on a remote destination as a workaround (bad — closed the only diagnostic escape hatch). Add: when a server-side coercion fires, surface it in the response/audit so operators see what was actually used.
4. **Schedule liveness ≠ backup liveness.** `last_run_at` advancing is "the cron tick claimed the schedule," not "the backup landed." The overdue detector should read the most recent `backup_runs` row's status, not just the schedule row.
5. **Format support landed earlier than format adoption.** IPAMBKP3 codec shipped in v3.24.0 with the restore-side dispatcher already aware of it. No production caller produced IPAMBKP3 archives until this hotfix wires the orchestrator. Codec presence ≠ codec adoption — track them separately in the changelog.
