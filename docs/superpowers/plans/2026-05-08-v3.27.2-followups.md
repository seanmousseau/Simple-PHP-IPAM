## 1. Scope

Four items, all carried forward from v3.27.1 decisions:

1. **Self-test CLI + UI button.** `tools/backup-self-test.php` plus a per-destination "Test backup" button sibling to the existing "Test connection". Full encrypt → upload → download → decrypt → byte-compare round-trip, behind step-up gate, writes a `backup_runs` row tagged `triggered_by='selftest'` that auto-deletes on success. New audit verbs: `backup.selftest_passed` / `backup.selftest_failed`. Q2 decision in v3.27.1 plan.
2. **Legacy IPAMBKP2 nudge.** UI banner on `backup_admin.php?tab=destinations` when the orchestrator has fallen back to `app_secret` (no vault key) in the last 7 days. Once-per-day `backup.legacy_path_used` audit row. Dismissible per-session. Q3 decision in v3.27.1 plan.
3. **Bug Y — MFA-disable lockout precondition guard.** Add `ipam_sudo_available_methods()`-based check to `disable_totp` / `email_otp_disable` / `passkey_delete` handlers in `change_password.php`. Refuse with actionable message ("would leave your account with no step-up method"). UX text must match the policy-save lockout guard's voice. v3.27.1 plan §9.1.
4. **Bug Z — step-up resume on vault_set** (CONDITIONAL). Verified during Pass A regression (`2026-05-08-v3.27.1-manual-regression-plan.md` §2.aa). If Pass A reproduces sean's "had to click Generate twice" symptom, fix lands here. If Pass A cannot reproduce, this item is closed with evidence and the slot is freed.

## 2. Out of scope (v3.28.0 or later)

- **Re-encryption tool for legacy IPAMBKP2 archives.** Migrating existing remote archives from IPAMBKP2 (app_secret) to IPAMBKP3 (vault key) is a one-shot ops operation and doesn't fit a minor release. Track separately.
- **Self-test history admin card.** A dedicated "past selftests" view with charts. Q2 option 3 in v3.27.1 plan; rejected for hotfix discipline. Revisit if operators ask.
- **Universal sudo-action precondition guard library.** Bug Y's fix is per-handler; a generic helper that every sudo handler invokes consistently is the correct end state but needs design (which actions actually need it? which are "destructive enough"?). v3.28.0 candidate.
- **Step-up policy that allows per-action TTL.** Today the TTL is install-wide. An advanced operator might want short TTL for vault reveal, longer for API key creation. Not an immediate need.

## 4. Working notes (to be expanded)

- **Self-test CLI shape:** `php tools/backup-self-test.php --destination <id> [--json] [--keep-artifact]`. Default deletes the synthetic remote object; `--keep-artifact` leaves it for inspection. JSON output for cron-monitorable healthchecks.
- **Self-test UI button placement:** beside "Test connection" on each destination row in `views/backup_admin_destinations.php`. Disabled while a real backup is in flight (concurrency guard via `ipam_backup_active_run_id()`).
- **Legacy banner copy (draft):** `"3 backups used the legacy IPAMBKP2 path in the last 7 days. Set up a backup vault key to migrate to IPAMBKP3."` — link to vault-key set flow. Count is a `SELECT COUNT(*) FROM backup_runs WHERE encryption_mode='stored' AND filename LIKE '%.enc' AND started_at > now() - 7 days` (or similar, verify the exact column semantics post-v3.27.1 deploy).
- **Bug Y guard helper:** `ipam_user_mfa_disable_lockout_check(\PDO $db, int $userId, string $methodToDisable): string` — returns empty string if the disable is safe, error message otherwise. Reuses `ipam_sudo_available_methods()` with a hypothetical-disable simulation. Three call sites.
